# Round 3 - Defense Report

## 対応した脆弱性
- **種別**: Decompression Bomb (Image Pixel Flood) in File Preview
- **OWASP分類**: A05:2021 - Security Misconfiguration (リソース制限の欠如)
- **深刻度**: Medium

## 修正方針
`image::ImageReader` にデコード制限 (`image::Limits`) を明示的に設定し、展開後のメモリ使用量とピクセル寸法を制限する。

**なぜこのアプローチを選んだか:**
- `image` クレート v0.25 が公式に提供している `Limits` API をそのまま利用でき、外部依存の追加が不要
- デコード処理の直前で制限が適用されるため、攻撃ベクタを正確にブロックできる
- 既存のチェーンメソッド呼び出しに最小限のコード追加で対応可能

**検討した他の選択肢:**
1. **`into_dimensions()` による事前チェック**: デコード前にピクセル寸法を取得する方法。追加のI/Oが必要で、一部フォーマットでは寸法取得に失敗する可能性がある。`Limits` API のほうがデコーダ内部で確実にチェックされるため却下。
2. **`MAX_IMAGE_SIZE` の引き下げ**: ディスクサイズ制限を厳しくする方法。圧縮率が高い画像（均一色PNG等）には依然として脆弱であり、根本対策にならないため却下。


## 副作用確認
- 既存テスト: 全30件通過（0 failed）
- ビルド: 警告なし（初回は `image::io::Limits` の非推奨警告が出たため `image::Limits` に修正済み）
- 動作確認:
  - 通常サイズの画像は制限値（8192x8192, 64MB）を大幅に下回るためプレビュー可能
  - 制限超過時は `image` クレートが `LimitError` を返し、`Err(_)` ブランチでテキスト/バイナリプレビューにフォールスルーするため、パニックは発生しない
  - デフォルト制限（512MB alloc）よりも厳しい値（64MB）を設定しているため、明示的な防御として機能する

## 残留リスク(あれば)
1. **64MB以下の展開サイズでの攻撃**: 64MBのメモリ消費は許容しているため、繰り返しファイル選択を行うことで累積的なメモリ圧迫を狙う攻撃は理論上可能。ただし、`image_protocol` は都度上書きされるため、同時に複数画像がメモリに残ることはない。
2. **エラー時のユーザー通知**: 制限超過でデコードが失敗した場合、テキスト/バイナリプレビューにフォールスルーするが、「画像が制限を超えている」旨の明示的なメッセージは表示されない。ユーザビリティの改善余地がある。
3. **アニメーション GIF のフレーム展開**: GIF のフレーム数が極端に多い場合、フレームごとのデコードでメモリが増大する可能性がある。`max_alloc` で一定の制限はかかるが、フレーム数自体の制限はしていない。

## 自己評価
- 修正の堅牢性(自己採点): 8/10
- 採点理由: `image` クレートの公式 `Limits` API を使用した正攻法の対策。ピクセル寸法（8192x8192）とメモリ割り当て（64MB）の両面で制限しているため、Decompression Bomb の主要な攻撃ベクタをカバーしている。減点要因は、エラー時のユーザー向けメッセージが不明瞭なことと、GIF フレーム展開など edge case の対策が限定的な点。
